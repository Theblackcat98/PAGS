Project constitution + delivery loop

PAGS.

Portable Agent Guide System: a small set of records and rules for repositories where AI agents do much of the work.

Agents forget between sessions. They add scope nobody asked for, change the architecture quietly, and make up reasons for old code. PAGS gives every project one written answer to each question an agent should ask before changing anything, plus a loop that keeps those answers current.

§1

Agents drift in three predictable ways

Each session starts with no memory of the last one. Without written records, small, reasonable-looking changes add up to a project nobody planned.

Scope creep

An agent adds a feature because it seemed useful. Nobody approved it, and now it has to be maintained.

PAGS: new capabilities need an approved roadmap item first.

Silent architecture change

A refactor swaps a pattern or adds a dependency. The next session cannot tell whether it was intended.

PAGS: hard-to-reverse choices get a decision record.

Invented history

In old code, agents guess why something was done and state the guess as fact.

PAGS: facts are marked observed, intended, or unknown.

§2

Four records, one question each

Records that change at the same pace live together. Intent (the charter) and reality (the architecture) stay apart, because keeping them apart is what makes PAGS honest about existing code. IDs like R-003 T-014 D-012 A-001 let entries point at each other.

AGENTS.md

How should I work here?

The loop, the change table, who may approve what, the project commands, and the definition of done. The only place commands are written.

.pags/CHARTER.md

What must not change casually?

Mission, goals, non-goals, principles, constraints, and the maintainer's name. One page. Only the maintainer edits it.

.pags/WORK.mdR- T-

What is approved, and what is being done now?

The Now block, then outcomes with their tasks indented underneath, then unplanned fixes and ideas for later.

.pags/DECISIONS.mdD-

Why was this chosen? Which rules are bent?

Decisions, dependency reasons, and exceptions. An exception is a decision with an end date and an exit condition.

.pags/ARCHITECTURE.mdA-

What exists today?

Structure, flows, interfaces, invariants, and known debt. Unconfirmed facts are marked observed or unknown.

README.md

What do users rely on?

The user-facing contract. Any change to visible behavior updates it in the same change.

.pags/DESIGN.mdoptional

What should it feel like?

Terms, states, visual language, and accessibility rules, for projects with an interface.

.pags/*-ARCHIVE.mdautomatic

What was finished or replaced?

Done tasks, finished outcomes, and replaced decisions move here, so the live files stay short.

§3

One line per entry, detail only when needed

Every entry starts with a headline line: ID, status in brackets, a summary, and links. Indented key: value lines add detail only where it earns its place. The headlines are the index, so there are no summary tables to keep in sync.

.pags/WORK.mdExample
- R-003 [approved] Offline edits sync when the network returns
  approved-by: sam 2026-09-20
  - T-014 [doing] Queue writes while offline -> D-012
    done-when: queued writes survive an app restart
  - T-015 [todo] Resolve conflicts on reconnect
.pags/DECISIONS.mdExample
- D-012 [accepted 2026-09-20] Use SQLite for the write queue -> R-003
  why: writes must survive restarts on mobile
  cost: adds a native build step
  replaces: D-004
- D-015 [exception until 2026-12-01] Skip e2e tests on Windows CI
  exit: runner image ships WebView2
One search lists every entry
$ grep -nE '^\s*- [RTDA]-[0-9]+' .pags/*.md
§4

The loop every agent follows

Each session goes through the same steps, from reading the handoff to writing the next one. The step that matters most is the scope check: work outside approved scope becomes a proposal and is not implemented.

§5

What each kind of change needs

One table in AGENTS.md replaces separate rules for classifying, reading, and recording. An agent finds its row, reads only what that row lists, and updates only what it names.

ChangeRead firstThen update
New capabilityCharter, WorkOutcome approval, then a task
Scope or non-goal changeCharter, WorkProposal approval, then Charter, Work, and a decision
Architecture or public interfaceArchitecture, DecisionsDecision, Architecture
New or removed dependencyDecisionsDecision starting “Add dependency:”, lockfile
RefactorArchitecture, relevant decisionsTask; Architecture if the structure changes
Security changeDecisions, ArchitectureTask; a decision if a policy changes
Bug fixArchitecture for the affected areaTask under Unplanned, regression test
User-visible behaviorREADMEREADME, in the same change
Temporary rule deviationThe rule being bentException in Decisions, with end date and exit approval
Maintenance, formatting, doc fixesNothing extraNothing new, as long as scope is unchanged

If a row names a record the project does not have yet, the agent creates it from the template. A minimal install never leaves an agent pointing at a file that does not exist.

§6

Agents propose. A named person approves.

This is the rule the rest of PAGS depends on. Approval should also be quick: when the maintainer says yes in the middle of a session, the agent records the approval and carries on.

Agents may
  • Draft roadmap outcomes and decisions as proposed
  • Create and progress tasks inside approved scope
  • Record evidence, observations, and unknowns
  • Write the Now block for the next session
Only the maintainer may
  • Approve roadmap outcomes
  • Accept decisions
  • Grant exceptions
  • Change the charter
§7

How each record moves

Each record type has a short, fixed list of statuses written in brackets. pags check rejects any status that is not on the list. Finished entries move to an archive file.

§8

New projects and existing ones

A new project starts with a one-page charter and grows its records as it grows. An existing project starts by describing what is there, without pretending anyone planned it.

Greenfield

A new repository with little or no code.

  1. Write a one-page charter before choosing a stack.
  2. Define three to seven roadmap outcomes.
  3. Add the first few tasks.
  4. Set build, test, lint, and format commands early.
  5. Record only decisions that are expensive to reverse.
  6. Start the architecture record once real structure exists.

Brownfield

An existing codebase with history and habits.

  1. Inventory the stack, commands, tests, and deployment.
  2. Describe observed behavior in the architecture record.
  3. Establish a test and CI baseline.
  4. Backfill decisions only for important choices; mark unknown reasons as unknown.
  5. Sort every existing problem into its record (below).
  6. Apply the rules to new work first, then improve old areas gradually.
Observed

Seen in the code or its behavior today. Goes in ARCHITECTURE, marked (observed).

Intended

Someone with authority decided it. Goes in CHARTER, WORK, or DECISIONS.

Unknown

Nobody knows why. Written as why: unknown and never guessed.

§9

The installer

One Python script with no dependencies sets PAGS up in any repository. It never overwrites your work silently: the default at every prompt is the safe choice, and it previews every change before writing.

§10

Rules that are checked, not only written

Agents follow written advice less reliably as their context fills up. pags check is a small script, installed as .pags/check.py, that runs before each commit and in CI. It fails the build when the records stop agreeing with each other.

  • Every ID is unique, sits in its own file, and every ID mentioned exists
  • Status values come from each record's allowed list
  • Tasks sit under an approved outcome or under Unplanned
  • Done tasks have evidence
  • Replaced decisions have a newer decision pointing at them
  • No placeholders are left once the charter is accepted
  • No exception is past its end date
$ python3 .pags/check.pyExample
.pags/DECISIONS.md:9: error: D-015 exception ended 2026-09-01; resolve it or ask the maintainer
.pags/WORK.md:14: error: T-022 links to R-009, which does not exist
.pags/WORK.md:31: warning: T-018 is [done]; move it to WORK-ARCHIVE.md
FAIL 41 entries, 2 error(s), 1 warning(s)
§11

Every session leaves a note for the next one

The Now block sits at the top of WORK.md. It is rewritten at the end of each session, not appended to, so it stays short enough for the next agent to read first.

.pags/WORK.mdExample
## Now

- Focus: R-003 offline sync. T-014 is in progress.
- Last session: Added the retry queue. Tests pass. D-012 accepted.
- Next: Handle conflicts on reconnect (T-015).
- Waiting on: Maintainer approval for the R-004 proposal.

<!-- Rewrite this block at the end of every session. -->
§12

Where PAGS fits

Spec-driven tools help write a spec for each feature. PAGS governs the whole project over time, so the two work well together.

Per-feature spec tools

  • Examples: GitHub Spec Kit, Kiro
  • One spec, plan, and task list per feature
  • Focused on getting a single feature built well
  • Guidance files describe the product and the stack

PAGS

  • One set of records for the whole life of a project
  • Honest about existing code: observed, intended, or unknown
  • Decisions are replaced, never rewritten
  • Exceptions expire unless someone renews them
  • Scope gates that agents cannot open themselves
§13

Still being decided

These parts of the design have options on the table but no decision yet. Each links to its issue.

  • #17

    Where the records live

    A hidden .pags/ folder is skipped by ripgrep and many agent search tools. A visible docs/pags/ folder avoids that.

  • #13

    IDs that cannot collide

    Two branches that each add a decision will both pick the next number. The archive keeps files short, but the ID scheme still needs a fix, or pags check needs to catch duplicates at merge.

  • #11

    Where the approver is named

    The rule in §6 is settled in principle. The open question is whether the name goes in the charter, AGENTS.md, or a CODEOWNERS-style line.
